# 1. Цели мониторинга в контексте «Александрит»
| Цель | Как измеряем | Связь с проблемами |
|------|--------------|--------------------|
| Обнаружить переполнение очередей RabbitMQ | Длина очередей, количество dead-letter | Проблема 1, 3 |
| Увидеть падение consumer'ов | Частота обработки сообщений, лаг consumer'а | Проблема 1, 4 |
| Контролировать время расчёта цены | Длительность операции расчета, количество полигонов | Проблема 3, R3 |
| Обнаружить рассинхрон между MES DB и CRM DB | Количество заказов в разных статусах | Проблема 1, 3 |
| Измерить производительность дашборда MES | Время ответа MES API, загрузка страницы | Проблема 2, R2 |
# 2. Мотивация: зачем компании мониторинг
## Текущая ситуация (слепое управление)
На данный момент компания не имеет инструментального взгляда на работу ключевых систем:
* Неизвестна реальная длина очередей в RabbitMQ — заказы накапливаются, но менеджеры узнают об этом только из жалоб.
* Нет информации о том, падал ли consumer (CRM API или MES API) — заказы теряются бесшумно.
* Время расчёта цены — «чёрный ящик»: никто не видит, какие модели или операторы вызывают задержки до 30 минут.
* Состояние синхронизации между MES DB и CRM DB не контролируется — рассинхрон выявляется только при сверке вручную раз в неделю.
* Дашборд MES тормозит, но неизвестно, насколько именно и стало ли лучше после изменений.
**Бизнес-результат:** рост жалоб, потеря B2B-контрактов, падение доверия к IT-системе.
## Что даст внедрение мониторинга (по ролям)
| Роль | Что получает | Как меняется работа |
|------|--------------|---------------------|
| Продакт-менеджер | Дашборд «Здоровье системы» в Grafana | Может сам увидеть рост очереди до жалоб клиентов. Приоритизирует баги на основе данных, а не эмоций |
| DevOps / SRE | Алерты в Telegram при падении consumer'а или переполнении очереди | Реагирует за 5 минут, а не через час после звонка от продавца |
| Тимлид | Время расчёта цены (p95) и его корреляция с полигонами | Может доказать бизнесу: нужна оптимизация алгоритма или докупать мощности |
| Операторы MES | Косвенно — ускорение дашборда | Увидят эффект от кеширования (Task5) → начнут доверять системе |
| B2B-партнёры | Прозрачность: компания быстрее чинит инциденты | Снижение оттока партнёров, рост API-трафика |
| Бизнес (владелец) | Метрика «доля заказов, зависших в расчёте >1 часа» | Объективный показатель качества IT |
## Экономическое обоснование
| Потери сейчас (в месяц) | После внедрения мониторинга |
|------------------------|------------------------------|
| 3 крупных B2B-контракта × 500 000 руб. = **1.5M руб.** | Снижение потерь на 80% → экономия **1.2M руб./мес** |
| 20 часов работы DevOps/тимлида на ручное расследование × 3000 руб/час = **60 000 руб.** | Снижение до 5 часов → экономия **45 000 руб./мес** |
**Консервативная оценка:** мониторинг окупается **за 1–2 месяца**.
# 3. Выбор подхода к мониторингу
## Какой подход и для чего
В системе «Александрит» я комбинирую **три подхода** для разных уровней:
| Подход | Где применяем | Почему |
|--------|--------------|--------|
| **RED** (Rate, Errors, Duration) | MES API, CRM API, Shop API (пользовательские сервисы) | API — интерфейс для клиентов. Важно знать: сколько запросов, сколько ошибок, какая задержка |
| **USE** (Utilization, Saturation, Errors) | RabbitMQ, базы данных, S3 (инфраструктурные компоненты) | Эти ресурсы имеют лимиты. Важно не перегрузить их |
| **Четыре золотых сигнала** (Latency, Traffic, Errors, Saturation) | Сквозные бизнес-процессы (заказ от создания до отправки) | Для ответа на вопрос: «доволен ли клиент?» |
## Итоговая матрица подходов
| Система / компонент | RED | USE | 4 сигнала | Приоритет |
|---------------------|-----|-----|-----------|-----------|
| MES API | ✅ | — | — | Critical |
| CRM API | ✅ | — | — | High |
| Shop API | ✅ | — | — | Medium |
| RabbitMQ | — | ✅ | — | Critical |
| PostgreSQL (все БД) | — | ✅ | — | High |
| S3 storage | — | ✅ | — | Medium |
| Сквозной заказ (B2B) | — | — | ✅ | Critical |
| Сквозной заказ (B2C) | — | — | ✅ | High |
| Дашборд MES (UI → API → БД) | ✅ | — | — | High |
# 4. Стек мониторинга
| Компонент | Технология | Обоснование |
|-----------|-----------|-------------|
| Сбор метрик | Prometheus | Бесплатно, стандарт индустрии, Managed в Yandex Cloud |
| Визуализация | Grafana | Поддержка Prometheus, алерты, дашборды «из коробки» |
| Алертинг | Alertmanager + Telegram | Быстро, дёшево, вся команда видит |
| Сбор метрик RabbitMQ | rabbitmq_exporter | Готовое решение, без кода |
| Сбор метрик БД | prometheus-postgres-exporter | Стандартный exporter |
**Почему не Datadog/New Relic:** дорого при росте числа заказов, нужен внешний SaaS, избыточно для MVP.
# 5. Метрики для отслеживания
## 5.1 Как выбирались метрики
| Категория | Подход | Типы метрик | Приоритет |
|-----------|--------|-------------|-----------|
| Пользовательские сервисы | RED | RPS, latency, errors, одновременные сессии | Critical |
| Инфраструктура | USE | CPU, RAM, connections, saturation | Critical |
| Бизнес-процессы | 4 сигнала | Сквозная задержка, потерянные заказы | High |
### Что НЕ взял (и почему):
| Метрика | Почему не взял |
|---------|----------------|
| `Number of requests per user` | Раздувает метрики (кардинальность 10k+). Для отладки используем трейсинг |
| `Kb transferred/received` | Не влияет на текущие проблемы (заказы теряются) |
| `Size of S3 storage` | Полезна, но не критична. Добавим позже |
## 5.2 Метрики для MES API (C#) — приоритет Critical
| Метрика | Зачем | Ярлыки (labels) |
|---------|-------|-----------------|
| RPS для MES API | Отслеживать рост нагрузки от B2B партнёров и операторов | `endpoint`, `method`, `client_id` |
| Response time (latency) для MES API | Измерить эффект от кеширования дашборда. Цель: p95 < 1 сек | `endpoint`, `quantile` |
| Number of HTTP 500 для MES API | Быстро обнаружить падение API. Каждая 500 = потерянный заказ | `endpoint`, `client_id` |
| Число одновременных сессий MES API | Понять, сколько операторов активно. При росте > 50 → масштабировать | `scope` |
### Дополнительные метрики (не из списка):
| Метрика | Зачем | Ярлыки |
|---------|-------|--------|
| `mes_price_calculation_duration_seconds` | Понять, какие модели считаются дольше всего | `polygon_range` |
| `mes_price_calculation_queue_length` | Длина очереди асинхронных расчётов | `priority` |
| `mes_dashboard_request_duration_seconds` | Время ответа дашборда (ключевая для операторов) | — |

## 5.5 Метрики для RabbitMQ (USE подход)
| Метрика | Зачем | Ярлыки | Порог насыщения |
|---------|-------|--------|-----------------|
| Number of dead-letter-exchange letters | Потерянные заказы. Каждое письмо в DLQ — инцидент | `queue`, `reason` | > 0 → critical |
| Number of messages in flight (unacked) | Consumer завис → очередь блокируется | `queue` | > 50 → warning |
| Длина очереди (messages_ready) | Заказы ждут обработки | `queue` | > 500 → warning, > 2000 → critical |
### Дополнительные метрики:
| Метрика | Зачем | Ярлыки |
|---------|-------|--------|
| `rabbitmq_queue_consumer_count` | Нет consumer'а → очередь никогда не опустеет | `queue` |
| `rabbitmq_queue_messages_redelivered` | Сообщения возвращаются в очередь (ошибка обработки) | `queue` |
## 5.6 Метрики для инфраструктуры (USE)
| Метрика | Зачем | Ярлыки | Порог насыщения |
|---------|-------|--------|-----------------|
| CPU % для API | Утилизация процессора → нужно ли масштабировать | `service` | > 80% → warning, > 90% → critical |
| Memory Utilisation для API | Утечки памяти → OOM Kill | `service` | > 85% → warning |
| Memory Utilisation для БД | PostgreSQL использует память под кеш | `db_name` | > 90% → warning |
| Number of connections для БД | Превышение max_connections → ошибки | `db_name` | > 80% от max → warning |
| Size of БД | Планирование дискового пространства | `db_name` | > 80% → warning |
## 5.7 Сквозные бизнес-метрики (4 золотых сигнала)
| Сигнал | Метрика | Зачем | Ярлыки |
|--------|---------|-------|--------|
| Latency | `order_end_to_end_duration_seconds` | Время от SUBMITTED до CLOSED | `order_type` |
| Traffic | `orders_created_per_hour` | Прогнозировать рост нагрузки | `source` |
| Errors | `orders_lost_total` | Заказы, которые не дошли до CRM | `reason` |
| Saturation | `queue_messages_ready / queue_limit` | Насколько очередь заполнена | `queue` |

## 6.2 MES API (C#) — OpenTelemetry
```csharp
// Program.cs
using OpenTelemetry.Metrics;

builder.Services.AddOpenTelemetry()
    .WithMetrics(provider => provider
        .AddAspNetCoreInstrumentation()
        .AddHttpClientInstrumentation()
        .AddMeter("Alexandrite.MES")
        .AddPrometheusExporter());

// Пользовательские метрики
public class MetricsService
{
    private readonly Histogram<double> _priceCalcDuration;
    private readonly Counter<int> _priceCalcCounter;

    public MetricsService(IMeterFactory meterFactory)
    {
        var meter = meterFactory.Create("Alexandrite.MES");
        _priceCalcDuration = meter.CreateHistogram<double>("mes_price_calculation_duration_seconds");
        _priceCalcCounter = meter.CreateCounter<int>("mes_price_calculation_total");
    }

    public void RecordPriceCalculation(double seconds, bool success)
    {
        _priceCalcDuration.Record(seconds);
        _priceCalcCounter.Add(1, new KeyValuePair<string, object>("status", success ? "success" : "failed"));
    }
}
```

## 6.5 Бизнес-метрики (Python exporter)
```python
from prometheus_client import Gauge, start_http_server
from sqlalchemy import create_engine, text
import time

stuck_gauge = Gauge('orders_stuck_in_price_calculated', 'Orders stuck >1h')

def collect():
    engine = create_engine('postgresql://user:pass@crm-db:5432/crm')
    with engine.connect() as conn:
        result = conn.execute(text(
            "SELECT COUNT(*) FROM orders WHERE status='PRICE_CALCULATED' AND updated_at < now() - interval '1 hour'"
        ))
        stuck_gauge.set(result.scalar())

if __name__ == '__main__':
    start_http_server(8000)
    while True:
        collect()
        time.sleep(30)
```
# 7. Алерты (Alertmanager)
Файл alerts.yml
```yaml
groups:
  - name: rabbitmq_alerts
    interval: 30s
    rules:
      - alert: RabbitMQQueueHigh
        expr: rabbitmq_queue_messages_ready{queue="crm_b2c"} > 2000
        for: 2m
        labels:
          severity: critical
        annotations:
          summary: "Очередь {{ $labels.queue }} переполнена"
          description: "{{ $value }} сообщений ждут обработки"

      - alert: RabbitMQNoConsumers
        expr: rabbitmq_queue_consumer_count == 0
        for: 1m
        labels:
          severity: critical
        annotations:
          summary: "Нет consumer'а для очереди {{ $labels.queue }}"

      - alert: DeadLetterQueueNonEmpty
        expr: rabbitmq_queue_messages_ready{queue="dead.letters"} > 0
        for: 0m
        labels:
          severity: critical
        annotations:
          summary: "Потерянные заказы в DLQ"

  - name: mes_alerts
    rules:
      - alert: PriceCalculationTooLong
        expr: histogram_quantile(0.95, rate(mes_price_calculation_duration_seconds_bucket[5m])) > 600
        labels:
          severity: warning
        annotations:
          summary: "Расчёт цены слишком долгий (p95 > 10 мин)"

      - alert: MESApiHighErrorRate
        expr: rate(mes_api_requests_total{status=~"5.."}[5m]) / rate(mes_api_requests_total[5m]) > 0.1
        for: 2m
        labels:
          severity: critical

  - name: business_alerts
    rules:
      - alert: OrdersStuckInPriceCalculation
        expr: orders_stuck_in_price_calculated > 20
        labels:
          severity: warning
        annotations:
          summary: "{{ $value }} заказов зависли в статусе PRICE_CALCULATED > 1 часа"

      - alert: OrdersLost
        expr: orders_crm_mes_diff > 0
        labels:
          severity: critical
        annotations:
          summary: "Обнаружен рассинхрон между MES DB и CRM DB"
```

# 9. Показатели насыщенности и пороговые значения
## 9.1 Ключевые показатели насыщенности
| Ресурс | Показатель | Порог (warning) | Порог (critical) | Почему именно этот порог |
|--------|-----------|-----------------|-----------------|--------------------------|
| RabbitMQ очередь | messages_ready / memory_limit | 50% (1000 сообщений) | 80% (4000) | RabbitMQ сбрасывает на диск при 50% памяти |
| Consumer RabbitMQ | consumer_count | < 1 | — | Без consumer'а очередь никогда не уменьшится |
| CPU API | utilization | 80% | 90% | При 80% рост latency. При 90% — риск OOM |
| Connection pool БД | active / max_connections | 80% | 95% | При 100% новые запросы падают с ошибкой |
| Диск БД | used / total | 80% | 90% | PostgreSQL требует места под WAL |
| Dead Letter Queue | количество сообщений | > 0 | > 0 | Каждое сообщение = потерянный заказ |
## 9.2 Что делать при превышении порогов
| Ресурс | Автоматическое действие | Ручное действие |
|--------|-------------------------|-----------------|
| Очередь > 2000 | — | Создать тикет, увеличить количество consumer'ов |
| CPU API > 90% | HPA добавит под (в K8s) | Уведомление в #alerts-platform |
| Connection pool > 80% | — | Увеличить max_connections, проверить утечки |
| DLQ не пуста | — | On-call инженер смотрит причину, перезапускает consumer'а |
| Диск БД > 90% | — | Добавить volume, запустить VACUUM FULL |
## 9.3 Процесс реакции
| Уровень | Действие | Время |
|---------|----------|-------|
| Warning | Jira-тикет + Telegram #alerts-warning | 5 минут |
| Critical | Telegram #alerts-critical + SMS/звонок | моментально |
| Critical | Вызов on-call (если не ответил за 10 минут) | 10 минут |

# 11. Результат внедрения
| Проблема | Как мониторинг помогает |
|----------|-------------------------|
| Проблема 1 (задержки заказов) | Увидим длину очереди и зависших consumer'ов до жалоб |
| Проблема 3 (B2B не получил заказ) | Метрика рассинхрона БД покажет потерянные заказы |
| Проблема 2 (тормозит дашборд) | Метрика mes_dashboard_request_duration_seconds подтвердит улучшение |
| Задержки релизов | Позволит быстрее обнаружить регрессии в prod |
## Ключевые метрики успеха
| Метрика | Целевое значение |
|---------|------------------|
| MTTD (Mean Time To Detect) | с 2 дней до 5 минут |
| MTTR (Mean Time To Resolve) | с 6 часов до 30 минут |
| Доля потерянных заказов | с 2-3% до < 0.1% |
